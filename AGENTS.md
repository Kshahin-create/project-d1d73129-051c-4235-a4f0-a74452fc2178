# Architecture rules
- Task automation is an audited read-derived follow-up layer with stable source keys; completing a task never mutates booking, leasing or financial state, and task notifications apply source permissions before rendering.
- Dynamic roles and permission levels live in protected registry tables; audited writers manage assignments while legacy enum roles are synchronized compatibility projections, so custom roles never require schema changes.
- Staff invitation and deactivation use caller-authorized database writers before Auth service operations; service outcomes remain explicit, while tenant password-setting and password-changing link issuance are denied to staff.
- Admin navigation uses canonical record routes with parameter-preserving legacy redirects; record views and server-filtered lists reuse Phase 1 permissions, while per-user preferences and export audit requests use separate audited writers so navigation cannot change business state.
- Contracts and accounting use audited database writers and a receipt/allocation ledger; preserve legacy source precision and provenance, and do not cut over reporting until duplicate review and reconciliation succeed.
- Financial and enclosing booking/status writers acquire the same transaction advisory lock before row locks to serialize receipt reversals with manual leasing confirmation; legacy financial tables remain immutable, including service-role writes.
- Marketing campaigns collect customer and auth phone sources server-side, deduplicate into a durable audience snapshot, and atomically claim recipients; admin-only sends distinguish provider acceptance from delivery and never retry uncertain results automatically.
- Resolve booking-email unit areas through the shared email area helper, preferring explicit total area over floor area, so current and older clients produce consistent emails.
- Encode non-ASCII email HTML as numeric entities in the shared send helper before sending, to protect Arabic copy from downstream charset conversion; keep plain text as Unicode.
- Send each app email from its own feature function that derives the recipient from trusted data, because the browser must never choose recipients or templates.
- Use React Email's synchronous render for HTML and plain text because the pinned async renderer decodes UTF-8 chunks without streaming and corrupts Arabic characters at chunk boundaries.
- Define business dashboard metrics once in public metrics_* read functions; clients, API and Telegram consume role-checked snapshots and matching drilldowns, while legacy evidence reports remain explicitly separate to prevent premature financial cutover.
- Dashboard detail views are read-only and reuse existing plan coordinates without extending them; this preserves records and avoids unverified spatial claims.
- Dashboard exports use the shared local Excel helper with a separate scope sheet and unpaginated filtered rows; availability gates prevent incomplete reports.
- The executive dashboard owns only its building and financial-period scope; detailed reports mount separately with their own filters and reuse the same permission-gated query results, so detail exploration cannot change executive totals or duplicate realtime subscriptions.
- Owner period reporting uses projected automatic audit status transitions as its single event source, excluding insertion snapshots and duplicate manual logs; this avoids double-counting while making partial historical coverage explicit.
- Dashboard report discovery and read-only evidence review reuse the executive query results and scoped detail exports; this keeps reconciliation inspectable without new reads or inferred payment eligibility.
- Activities, building–activity links and activity-restricted units live in the database registry; the public site reads them only through public_* views and the bookingActivities module applies them at load (its seed is a pre-load fallback), so the site shows exactly what admins configure.
- Units carry publish_state and is_test separately from leasing status; publishing requires building, activity, unit type and area (enforced by trigger), and test units are excluded from public views and every metric.
- Unit imports go through a database dry-run preview and an apply function that recomputes the preview, rejects conflicts, writes audit_log per row and inserts new units as drafts.
- Keep public SEO routes and structured entity data in the shared SEO module; sitemap generation consumes the same whitelist to exclude session, account and management surfaces.
- Keep static homepage metadata and schema in index.html with route metadata through Helmet; client metadata cannot provide server-rendered social previews or real HTTP status codes.
- Serve compressed WebP renditions on public pages and retain a detailed plan for zoom; explicit intrinsic dimensions reserve layout space without altering source drawings.- External CRM integration goes through the read-only crm-api function with crm:* scoped, field-redacting keys; the legacy api function stays separate so CRM keys can never write.
- Unit availability is enforced in the database: a unit with a tenant or an active booking can never be 'available' (triggers block it and auto-reserve), so the public booking page can trust unit status.
- Register owner-supplied section location images in BuildingLocationPreview and render them above each unit plan; explicit building-section keys prevent showing a different section's location.
- Admin user details use an admin-gated read-only directory RPC with explicit contact fields and latest user-linked access records; never expose auth secrets or infer nationality from an IP location.
- Enforce administrative writes on the server as admin-only and gate matching UI controls; manager reads remain separate from mutations, including storage and Telegram operations.
- Apply activity-specific unit eligibility through the shared booking activity helper in counts, plan/list controls and selection; keep activity-only reservation display separate from persisted occupancy to preserve other activities and existing contracts.
- Centralize leasing transitions in the database-owned set_unit_status boundary; shared unit-status helpers are read/UI policy only, and legacy compatibility must never treat unresolved records as available.
- CRM: parties and opportunities are written only through SECURITY DEFINER functions (create_party, create_opportunity, move_opportunity, log_opportunity_activity, assign/transfer); stage moves sync automatically from booking/leasing triggers, sales agents read contacts only through the owner-masking parties_crm view, and possible duplicates go to duplicate_candidates for human review — never auto-merge.
- Data-quality checks live in the data_quality_findings_raw SQL view with resolutions in data_quality_resolutions (audited writer); unit_audit_log is frozen read-only — all entity timelines read audit_log via the shared AuditTimeline component.

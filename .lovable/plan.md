# المرحلة 1 / الطلب 4 — مصدر واحد لتغيير حالة الوحدة

## النتيجة المطلوبة
تغيير حالة التأجير من خلال وظيفة واحدة آمنة، مع حفظ السبب والمرجع والمنفّذ، ومنع أي تغيير مباشر من الصفحات أو البوت. التنفيذ يبدأ بعد الموافقة على الخطة فقط.

**اختياراتك:** الحجز المؤقت 48 ساعة، تمديد واحد فقط مع سبب، دور مستقل لمدير التأجير مع بقاء المدير الحالي للعرض فقط، وسجل عقد مرتبط بتحقق أول دفعة من إيصال موجود.

## ما كشفته المراجعة
- الموجود حاليًا: 598 متاحة، 73 محجوزة، 37 مؤجرة؛ الإجمالي 708 وحدات وقت المراجعة، وليس رقمًا ثابتًا في الواجهة.
- من المحجوزة: 3 مرتبطة بحجز معلّق غير منتهٍ، و61 عليها سجل مستأجر بلا حجز معلّق أو مؤكّد، و9 بلا أي من هذه المراجع. لذلك تحويل كل المحجوز إلى حجز مؤقت تلقائيًا غير آمن.
- تأكيد الحجز حاليًا يحوّل الوحدة لمؤجرة مباشرة؛ سيتم فصله عن التأجير النهائي.
- لا يوجد سجل عقود مستقل حاليًا. لن يُفترض أن سجل المستأجر أو رصيد المدفوعات يثبت عقدًا فعّالًا أو دفعة متحققة.
- إنهاء الحجوزات المجدول موجود بالفعل كل 5 دقائق؛ سنحافظ عليه ونوصل عمله بالوظيفة الجديدة، دون إضافة مهمة مكررة.

## 1. نقل الحالات بدون إتاحة خاطئة
إضافة نوع حالات جديد وعمود `units.leasing_status` بدل تغيير نوع أو حذف عمود `status` الموجود؛ العمود القديم يبقى قراءة فقط ومعلّمًا بأنه متقاعد.

| القيمة الحالية | النقل الموثّق |
|---|---|
| available | available بشرط عدم وجود إشغال أو حجز فعّال متعارض؛ المخالف للمراجعة |
| rented | leased مع توثيق أنها حالة تاريخية، دون اختلاق عقد أو تحقق دفعة |
| reserved | on_hold عند وجود حجز معلّق صالح وحيد ودون تعارض؛ pending_contract عند وجود حجز مؤكّد وحيد ودون تعارض |
| maintenance | maintenance مع مراجعة أي إشغال متعارض |
| reserved بلا دليل واضح، أو أي قيمة أخرى/تعارض | قائمة مراجعة مع الحفاظ على القيمة الأصلية؛ الحالة الجديدة غير محسومة، والوحدة غير متاحة للحجز |

تسجيل كل قرار نقل والسبب والمرجع في سجل التدقيق وسجل نقل مستقل. لا تحرير لوحدات مجهولة ولا تعديل أسعار أو مدفوعات تاريخية. لا إنشاء أحداث تأجير جديدة بتاريخ اليوم لتغييرات النقل التاريخي.

## 2. الوظيفة الوحيدة وقواعد الانتقال
`set_unit_status(unit_id, new_status, reason, ref_type, ref_id)` تكون `SECURITY DEFINER`، بصلاحيات محدودة ومسار بحث ثابت؛ تقفل سجل الوحدة، تتحقق من صلاحية المنفّذ والمرجع من السجلات الموثوقة، ثم تغيّر الحالة وتكتب التدقيق والتاريخ في نفس المعاملة.

- متاحة ← محجوزة مؤقتًا: حجز مسجل صالح؛ أو متاحة ← صيانة / موقوفة.
- محجوزة مؤقتًا ← بانتظار العقد: تأكيد الحجز؛ أو ← متاحة: انتهاء/إلغاء موثّق.
- بانتظار العقد ← مؤجرة: عقد فعّال + أول دفعة متحقق منها + تأكيد يدوي صريح؛ أو ← متاحة: إلغاء.
- مؤجرة ← متاحة: انتهاء أو إنهاء العقد الموثّق؛ الوحدات المؤجرة التاريخية تحتاج توثيق عقد قبل تحريرها بهذه العملية.
- صيانة / موقوفة ← متاحة: بعد التأكد من عدم وجود إشغال أو حجز فعّال.
- كل انتقال آخر مرفوض برسالة عربية، وكذلك المرجع غير الصحيح أو السبب الأقل من 5 أحرف.

صلاحية control تقتصر على متاحة ← صيانة ← متاحة، ولا تتيح تحرير مؤجرة أو محجوزة أو تحويلها لموقوفة. المدير الحالي عرض فقط. العميل ينشئ الحجز أو يلغيه من وظائف الحجز الخاصة به، وليس عبر تغيير حالة وحدة مباشرة.

## 3. الحجز والعقد وأول دفعة
- حفظ `hold_hours=48` و`max_hold_extensions=1` في إعدادات النظام؛ إنشاء الحجز يستخدمها من قاعدة البيانات، وليس من قيمة يرسلها المتصفح.
- التمديد مرة واحدة للحجز المعلّق غير المنتهي، لمدة الحجز المضبوطة في الإعدادات؛ لا إعادة فتح الحجز المنتهي بعملية تمديد. قفل السجل وعدّاد تمديد وتدقيق يمنعون تجاوز الحد بالطلبات المتزامنة.
- إضافة دور `leasing_manager` مستقل، يمنح التمديد فقط ضمن النطاق الحالي؛ لا تعديل تلقائي لأي حساب أو منح صلاحيات المدير القديم. تعيين الدور للأدمن فقط.
- إضافة سجل عقد مرتبط بالوحدة والحجز/حساب المستأجر، وحالة العقد وتواريخها ومراجعها، ووظائف آمنة لتسجيل تفعيله وانتهائه/إنهائه.
- إضافة تحقق أول دفعة مرتبط بإيصال مالي فعلي موجود: المنفذ، الوقت، السبب، والمرجع. الإيصال المؤرشف أو المعكوس غير صالح، ولا يُعتبر رقم الرصيد تحققًا.
- تأكيد الحجز ينقل إلى «بانتظار العقد» فقط. تسجيل الدفع لا يؤجر تلقائيًا. التأجير النهائي إجراء يدوي للأدمن بعد اكتمال الأدلة، دون اختراع نسبة سداد أو تعديل القيم المالية.

## 4. إغلاق كل مسارات الكتابة
إعادة توصيل وظائف الحجز والصيانة والمستأجرين والحذف الآمن والاستيراد ذات الصلة بالكاتب الوحيد، بما فيها التريجرز التي تحجز الوحدة تلقائيًا. أي بيانات إشغال تُعدّل داخل نفس المعاملة قبل محاولة تحرير الوحدة، مع منع الحجز المزدوج.

سحب صلاحيات UPDATE المباشرة على الحالة الجديدة والقديمة و`status_before_maintenance` من authenticated وanon، ومراجعة صلاحيات UPDATE على الجدول كله لأن منح الجدول يتجاوز سحب صلاحية عمود منفرد. حماية قاعدة البيانات تمنع الكتابة المباشرة أيضًا من وظائف الخدمة؛ لا الاعتماد على علامة قابلة للتزوير من المتصفح. الحالة القديمة لا تظل نسخة قابلة للتعديل.

الـAPI القديمة وCRM ومزامنة الشيت تظل قراءة فقط/دفع فقط كما هي؛ لن تُفتح لها عمليات تغيير حالة جديدة. الحالات غير المعروفة تظل أخطاء مراجعة ولا تتحول إلى متاحة.

## 5. العرض وسجل الوحدة
- تسميات الحالات الست في صفحة الوحدات، الحجز، المخططات، التقارير، البوت والشيت والتوثيق، من مصدر مشترك.
- فصل حالة النشر وكون الوحدة تجريبية وتخصيص النشاط عن حالة التأجير كما هو قائم.
- إظهار سجل زمني داخل نافذة الوحدة: من/إلى، المنفّذ، السبب، مرجع الحجز/العقد/الإيصال، التاريخ؛ صلاحيات قراءة إدارية فقط، مع تحميل صفحات من الخادم.
- قائمة مراجعة للحالات غير المحسومة، بحث وفلاتر وتصدير حسب الصلاحية، وتسوية بشرية عبر وظيفة مدققة لا تسمح بإتاحة وحدة عليها إشغال.
- الحفاظ على تعريفات اللوحة التنفيذية ونطاقها وأرقام الأموال؛ تعديل توافق حالات القراءة فقط، مع إبقاء التاريخ القديم قابلًا للتفسير دون احتساب النقل كعمليات تأجير جديدة.

## خطة الترحيل والتحقق
ترحيل إضافي قابل لإعادة التشغيل: النوع والأعمدة والسجلات والصلاحيات أولًا، ثم النقل الموثق، ثم الوظائف والحماية وواجهات القراءة. تغيير القرّاء والكتّاب معًا والتحقق قبل نشر الوظائف المتأثرة؛ لا نشر الموقع تلقائيًا. ينتهي الترحيل باستعلامات تحقق لعدد الوحدات والنقل غير المحسوم والصلاحيات، وتُرفق نتائجها وخطوات تشغيلها.

بعد التنفيذ:
1. اختبارات قاعدة بيانات لكل انتقال مسموح ومرفوض، والأسباب والمراجع، وحجزين متزامنين لنفس الوحدة؛ التحقق من التراجع الكامل عند فشل العملية.
2. اختبار 48 ساعة وتمديد واحد، ومنع التمديد الثاني والمتزامن ومنع المدير/control من تجاوز حدودهم.
3. إثبات أن UPDATE المباشر يفشل وأن API/الشيت لا يعيدان فتح الكتابة.
4. حجز اختباري معزول ← تأكيد ← بانتظار العقد؛ دفع بلا عقد/تحقق لا يؤجر؛ ثم عقد فعّال ودفعة متحققة وتأكيد يدوي ← مؤجرة؛ ثم نهاية عقد ← متاحة.
5. اختبار الإلغاء والانتهاء كل 5 دقائق وعدم تحرير وحدة عليها مرجع نشط آخر، والتاريخ والتدقيق مرة واحدة للعملية.
6. مقارنة عدد الوحدات والمدفوعات والمراجع قبل/بعد، واختبارات اللوحة والحجز والمخططات ومفاتيح API والتوثيق وMCP والبوت، مع استبعاد وحدات الاختبار من الجمهور والمؤشرات.

**خارج النطاق:** تغيير الأسعار، إعادة تفسير السداد التاريخي، تحرير الحالات المتنازع عليها تلقائيًا، حذف سجلات، أو إعادة تصميم الصفحات الأخرى.
